## What the Native12 / 1.0.3-12 monitor actually does
- View structure from Objective-C metadata: `CBDockSystemMonitorView : UIView` with four child `CBDockMetricItemView` (`_battItem`, `_tempItem`, `_cpuItem`, `_ramItem`), `NSTimer _refreshTimer`, previous CPU tick counters, `_showAll`. Each item contains an icon/fallback emoji/value label; monitor has `layoutSubviews`, `handleTapGesture:`, `setShowAll:`, `willMoveToWindow:`, `startMonitoring`, `stopMonitoring`, `updateMetrics`, `readDeviceTemperature`, `readCpuUsage`, `readRamUsage:total:`. Settings have `dockSystemMonitorEnabled` and `dockSystemMonitorShowAll`. **No separate GPU metric item or readGpuTemperature selector is shown by this metadata**, but absence of one selector in a bounded scan is not conclusive absence from all code.
- `startMonitoring` VM `0xb49dc` schedules repeating `NSTimer` into current runloop, **12.0 s collapsed / 5.0 s expanded**; invalidates previous timer. `stopMonitoring` VM `0xb4ad4` invalidates; `setShowAll:` VM `0xb42a8` requests layout, then stop/restart if already monitoring. `updateMetrics` VM `0xb4dbc` checks `isHidden`, `alpha`, `window`, `superview` before sampling; selector references `updateBatteryMetric` VM `0xb4e70`, `readDeviceTemperature` `0xb4e90`, `readCpuUsage` `0xb4fc0`. This is a sampled **display**, not an FPS optimizer or clock governor.
- `readDeviceTemperature` VM `0xb5230` (121 instructions directly inspected): queries `AppleSmartBattery` (ARM64 `0xb5248`), falls through to `AppleTemperatureSensor` (`0xb52f8`) and `AppleEmbeddedNVMeTemperatureSensor` (`0xb5318`), uses IOKit property read + `intValue`; if positive integer > 1000 scale by 100, if 1..1000 scale by 10. When no usable positive value, `[NSProcessInfo.processInfo thermalState]` at `0xb53c8` indexes a fixed Float32 table: **33.5, 38.0, 43.5, 48.0** degrees by nominal/fair/serious/critical; invalid thermal index has a fixed `35.0` path. These fallback values are **fabricated numeric estimates**, NOT measured sensor temperatures. `AppleSmartBattery` indicates battery, `AppleEmbeddedNVMeTemperatureSensor` storage, generic `AppleTemperatureSensor` unknown exact physical location: **neither a GPU-specific sensor nor actual GPU degrees Celsius is proven**. Even a plausible `xx °C` in the CarPlay Dock must not be advertised as measured GPU temperature without source selection evidence and on-device calibration.
- `readCpuUsage` VM `0xb5414`: `mach_host_self`/`host_statistics` `HOST_CPU_LOAD_INFO=3`, stores four previous CPU tick counters, uses busyDelta/totalDelta ×100. First sample **hard-coded 8.0%**, not real load; actual later samples represent **system-wide**, not GPU usage or single app CPU. `updateBatteryMetric` VM `0xb4b4c` reads `UIDevice.batteryLevel` / `batteryState`, enables battery monitoring if needed. `readRamUsage:total:` exists but exact formula and displayed GPU memory not re-disassembled in this turn.
- The first-party GPU/temperature interpretation must stay separate from DuoDash **Optimize CPU and Thermal** which changes `com.apple.airplay` private `maxFPS/encoderFPSFixed` keys to 15 in a DIFFERENT product ([report](https://github.com/chuongnguyen89dn-ui/Duoface/blob/spec-main/docs/duodash-113-optimize-cpu-thermal-arm64-analysis-20261016.md)). That is an FPS preference experiment, not a GPU-thermometer API.

## Exact CarPlay placement: established vs unknown
**Established by static metadata/log strings**:
- A CarPlay native **Dock-associated** system monitor is evidenced by `[CBHook_DockMonitor]` in the archived DuoFace reference scan (`sideplay/spec-knowledge/BAO_CAO_QUET_AZ_DUONAVI_VS_QA185.md`, line 59) and the test-build static log format `[DuoFaceDB] SystemMonitor applied targetFrame=%@ (dockMinY=%.1f, lowestItemY=%.1f, highestItemY=%.1f)` (`HO_SO_02.md`, line 1156). This strongly indicates dynamic frame placement **relative to native Dock bounds and existing Dock items**, rather than a universal screen-fixed `x/y`. The four child items are sized/shown via `CBDockSystemMonitorView.layoutSubviews` VM `0xb4604` (`setHidden:`, multiple `setFrame:` callsites), no app-pane insertion proven.
- For actual vendor-original DuoNavi **1.0.4**, separately SHA-pinned ARM64 geometry analysis shows `CBWindow.carPlayScreenBounds` VM `0xb0ddc` fetches external CarPlay scene/screen/display bounds; `CBWindow.carPlayContentInsets` VM `0xb1370` reads `[activeCarPlayWindow rootWindow] safeAreaInsets` with conditional **64 pt fallback only if necessary**, and `CBWindow.carPlayUsableBounds` VM `0xb15cc` subtracts those insets; `createWindows`, `resizeWindows` and `CBBridgedSplitApp.layoutSplitViews` use that usable area. This describes a **native Dock-safe geometry policy**, not an exact placement of the thermometer widget.
- DuoNavi original 1.0.4 injection filter explicitly includes CarPlay/CarPlayApp/Dashboard/SpringBoard and specific third-party apps, not one dedicated monitor process; this shows possible hosts, **does not identify monitor's runtime owner**. On user device, original external display observed once 640×331.333pt scale3 vs a separate session 640×360pt, so don't infer same physical coordinates (see `sideplay/audit/duonavi-original-live-20261030/DUONAVI_OBSERVER_PHYSICAL_LOG_V1_ABI_AND_CARPLAY_LOCK_VERDICT.md`).
**Still NOT established**:
- Original **DuoNavi 1.0.4** class-by-class readback confirming its actual monitor exists and uses same temperature selector/property (distinct original source is available but was not disassembled for this question).
- Exact parent UIWindow/CarPlay process, Dock subtree, frame `x,y,w,h`, monitor window level/z-order, whether left/right or top/bottom orientation and what happens during open picker, drag, reconnect, Home. A targetFrame format string is NOT a runtime frame sample; a connection filter is NOT proof view ownership.
- Whether original 1.0.4 specifically reads **GPU temperature**, whether any sensor provides a GPU ID, or whether display seen on user's car has a real measured Celsius reading.
